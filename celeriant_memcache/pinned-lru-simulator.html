Mechanics to look for

  • The first pin moves a value out of the LRU; the last unpin moves it back as most recent. Overlapping requests share one slot, counted by ×n.
  • len() counts loaded reservations, so it can pass cap. Every "cache full" check in ShardMemCache trips early while pins are live.
  • Releasing a large request can flush the LRU: see large release flush, where the just-read key 1 is evicted.
  • Recency isn't tracked while a key is reserved. A key reserved long ago comes back ahead of keys used since.
  • clear (rollback) drops values and keeps reservations. A key showing ? must be reloaded before validation can decide.
  • An unbalanced unpin panics in Rust. Only ValidationPins can call it, so that needs a bug in the guard.
  • Not shown here: the reservation table shrinks back to about max(cap, 2 × live) slots after a large release.
