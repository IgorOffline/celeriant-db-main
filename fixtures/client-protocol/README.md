# Conflict response fixtures

Assignments in `assignments.txt` and `docs/client-protocol.md` are frozen for client protocol 0.3.0. Files contain raw bytes, without text or hex wrappers. `v4` uses fixed-width little-endian bincode; `v5` uses MessagePack arrays and the existing binary aggregate-key representation.

Each `.body.bin` holds the ordered fields `(correlation_id, conflicts)` and applies to both operations. Each `.frame.bin` adds the 17-byte uncompressed header with the version and operation-specific type ID (write 13, delete 14). All fixtures fit below the compression threshold.

Every fixture has correlation ID `u128::MAX`. A conflict is `(key, expected, current)`, with key fields `(org_id, aggregate_type_id, aggregate_id)`.

| Case | Keys, in transport order | Expected/current |
| --- | --- | --- |
| single | `(u128::MAX, u128::MAX, u128::MAX)` | `(u64::MAX, 0)` |
| many | `(1,1,255)`, `(1,1,256)`, `(1,256,0)`, `(255,0,0)`, `(256,0,0)` | Record index `i` has `(u64::MAX-i, i)` |

The many-key case deliberately distinguishes unsigned numeric order from little-endian byte order. Binary files were frozen from independently declared contract-only response shapes through the existing codec APIs before production conflict response types were implemented. They are not regenerated by tests.

Run `cargo test --offline -p celeriant_msg --test occ_conflict_protocol` to verify final response types, full-frame dispatch, vector boundaries, truncation, size ceilings and compression expansion fallback.
